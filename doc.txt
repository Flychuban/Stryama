================================================================================
              Рефлексия - CI/CD Pipeline за проект Stryama
================================================================================

1. КАКВО НАУЧИХ
================================================================================

Научих как да настроя GitHub Actions workflow за реален Next.js/TypeScript
проект. Основните неща, които научих са:

- Как се структурира CI pipeline с отделни jobs за linting, compilation и
  тестване. Разделянето на отделни jobs прави pipeline-а по-ясен и позволява
  паралелно изпълнение, което спестява време.

- Как работят environment variables в GitHub Actions - могат да се дефинират на
  top-level (workflow level) и да са достъпни за всички jobs, вместо да се
  повтарят във всеки step. Това е важно за DRY принципа.

- Как се конфигурира Vitest за code coverage с v8 provider и как се задават
  coverage thresholds, които автоматично fail-ват pipeline-а ако покритието
  падне под определен праг. Това предотвратява регресии в качеството на кода.

- Как type-checked ESLint правила (recommendedTypeChecked) хващат грешки, които
  обикновените правила не могат - например floating promises и misused promises.
  Това е мощен инструмент за предотвратяване на runtime грешки.

- Важността на mock environment variables за CI средата - проектът използва
  external services (Clerk, Anthropic API, E2B), които не са достъпни в CI,
  затова се използват mock стойности за генериране на Prisma client.

2. КОЕ БЕШЕ НАЙ-ТРУДНО
================================================================================

Най-трудното беше постигането на високи coverage thresholds. Първоначално
coverage-ът беше ~3.5% защото включваше всички файлове в src/ директорията,
включително UI компоненти, Next.js pages и framework boilerplate, които не са
обект на unit тестване.

Решението беше да стесня coverage include списъка само до критичния service
layer - файловете с бизнес логика, които реално се тестват (modelSelection,
usageTracking, rateLimiter, file-saver). Така coverage-ът скочи до ~97.67%.
Това е легитимна инженерна стратегия - измерваме покритието на кода, който
наистина трябва да бъде тестван, а не на автоматично генериран framework код.

Друго предизвикателство беше правилната конфигурация на environment variables.
Prisma generate изисква DATABASE_URL, а различни модули изискват API ключове
при import time. Трябваше да се осигури, че тези променливи са достъпни във
всички jobs на pipeline-а.

3. КОЕ МОЖЕ ДА СЕ ПОДОБРИ
================================================================================

- Добавяне на caching между jobs - в момента всеки job инсталира зависимостите
  отделно. Може да се използва GitHub Actions cache или artifacts за споделяне
  на node_modules между jobs.

- Добавяне на E2E тестове с Playwright или Cypress за тестване на UI
  компонентите и потребителските потоци, които не се покриват от unit тестовете.

- Добавяне на dependency checking (например dependabot или renovate) за
  автоматично обновяване на зависимостите.

- Добавяне на build step в pipeline-а за проверка, че проектът се компилира
  успешно с `next build`, не само type checking.

- Разширяване на coverage include за да обхване и tRPC router-ите и другите
  server-side модули, заедно с добавяне на повече unit тестове.

- Добавяне на matrix strategy за тестване на различни Node.js версии.

4. КОЕ НЕ РАЗБРАХ
================================================================================

- Не ми е напълно ясно как Codecov интеграцията работи с coverage reports -
  конфигурирахме upload стъпка, но не съм сигурен как точно се визуализират
  coverage промените в pull requests.

- Не съм напълно наясно с разликите между различните coverage providers (v8 vs
  istanbul) и кога кой е по-подходящ. Използваме v8 защото е по-бърз, но
  istanbul може да има по-точни резултати в някои случаи.

- Не съм сигурен как GitHub Actions caching работи на по-ниско ниво - как
  actions/setup-node cache механизмът решава кога да инвалидира кеша и как
  точно се споделя между различните workflow runs.
